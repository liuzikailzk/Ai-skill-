# 来源、版本与同步

## 能力与边界

维护端已保存文件 → **手动导入** → Codex 仓库 → GitHub 历史副本 → **未接通** → ChatGPT 制作会话。

没有可用的跨 ChatGPT 聊天读取/投递工具；同步脚本不产生访问权限。当前只能由用户手动导出、上传文件到各会话。附件是否能被某个制作会话完整读取，必须在那个会话验证。未来若提供受支持的 GitHub 连接，也要用具体制作会话读取清单和文件验证，不能借用 Codex 的访问测试。

## 版本规则

- 基线为 1.0。维护端在北京时间 2026-10-16 发布 1.1、2026-10-23 发布 1.2，此后周五递增；1.9 后为 1.10。
- Codex 不按日期自动升版，不推测尚未发布的版本。维护端未确认版本与修订时暂停真实导入。
- 同一周版本可以有多次修订。对比 `weekly_version`、`revision` 和 `content_sha256`；只比较 1.0 不足以判断一致。
- 修订标识由维护端确认，每套 Skill 中唯一；保存时间采用带时区的 ISO 8601，例如北京时间 `2026-10-12T09:30:00+08:00`。不能虚构保存时间。
- 每套完整文件清单逐文件采用 SHA-256；`content_sha256` 是路径与校验值映射的规范 JSON 的 SHA-256，能识别删除、增加及改名。

## 首次最少交接材料

用户只需提供 **一个 ZIP**：三套 Skill 的完整目录，加一份维护端保存说明。没有新正文时，不创建空的 Skill 或沿用未经确认的旧备份。

```text
维护端导出包/
  script-visual-assets/SKILL.md
  script-visual-assets/实际引用、脚本和资源...
  script-video-shot-director/SKILL.md
  script-video-shot-director/实际依赖...
  manga-reasoning-storyboard/SKILL.md
  manga-reasoning-storyboard/实际依赖...
  维护端保存说明（文本或 JSON）
```

保存说明应由维护端确认：每套的周发布版本、最新修订标识、成功保存时间、完整文件列表，以及“这些文件已经成功保存且是此次导出的最新版”。若没有已有修订标识，由维护端先确认标识，Codex 不代发规则版本。若依赖跨出 Skill 目录，保持原始目录关系并报告；不能擅自移动或改写链接，当前工具会拒绝跨包引用，届时按真实布局扩展导入器。

SHA-256 和机器格式可由 Codex 从收到的原始字节生成，用户不需要手工填写或写代码。必须先与维护端提供的完整文件列表比对；本地计算校验值本身不证明源文件完整，也不证明维护端保存成功。源真实性当前依赖维护端说明，尚无独立查询通道。

## Codex 执行步骤

1. 查看本地改动和远端最新提交。用现有 Git HTTPS 认证读远端；有其他改动先保留并处理，不能强制覆盖。收到 ZIP 时在临时目录检查文件名、大小和路径，再安全解包，拒绝绝对路径、`..` 路径和符号链接。
2. 核对维护端保存说明及完整列表。将清单与现有 `registry/latest.json` 对比。后续导出须确认基于当前记录的维护端修订；把对应内容摘要填写到 `parent_content_sha256`。首次为 null。若导出来源与前一修订不一致，先回维护端确认，不能自行“修复”父标识来通过校验。
3. 在临时导入目录放每套完整目录和 `release.json`（见下）。说明文件可保存在交接档案中，导入根目录仅放 `release.json` 和此次声明的 Skill 目录。
4. 执行 `python3 tools/skill_sync.py import /tmp/已核对的导入目录`。工具要求显式“已保存”声明及保存依据，校验完整列表、摘要、普通 Markdown 行内引用、父修订、时间和版本；拒绝旧修订、重复标识与旧内容复活。重复的同一份导出是无变更操作。
5. 运行 `python3 tools/skill_sync.py verify`，查看清单差异、删除记录和依赖检查结果。脚本动态依赖、Markdown 参考式链接、运行行为仍需按真实 Skill 检查，不能把哈希校验称为功能测试。
6. 提交工具生成的清单与所有新快照，使用普通 Git push 保存；然后比较本地提交 SHA 与远端目标分支 SHA。初次空仓库可建立 main；已有仓库遵守其分支约定，不强推。
7. 更新文档中的同步证据，记录提交 SHA、源版本与修订、推送结果。导入清单的 `sync_status: manual_import_local` 表示本地导入事实，不能自行解读为 GitHub 或生产会话已同步。`channels.codex_to_github: pending_push` 在每次新导入时重置；推送确认后才能记录为已推送，记录的提交与来源必须可追溯。
8. 导出生产交付包：`python3 tools/skill_sync.py export /tmp/skills-production.zip`。工具先校验文件；交付包包含最新版清单、最新正文与依赖、接入说明，不包含旧规则文件。通过可用的文件交付方式提供给用户；不能把仅存在于 Codex 的 `/tmp` 路径说成另一个 ChatGPT 会话可访问的地址。
9. 用户将交付包和指令分别上传到制作会话。由它实际读取所需正文和引用，并输出读取回执。将收到的真实回执记录在独立文档，记录会话/项目、时间、来源、版本、修订、实际读取的引用内容；没有回执保持未验证。
10. 此后每个新制作请求先取最新版清单。文件没变且已在当前会话加载时沿用；修订变化则重新读取所需完整文件。没有可访问来源或最新清单时，明确停留版本及最后核对时间；手动交付只证明“截至交付时”的副本，不能宣称维护端此刻绝无更新。

用户无需运行这些命令；将已保存导出包交给 Codex，并要求执行本流程即可。

## `release.json` 机器交接格式

下面仅为字段示例，不是任何真实 Skill 的内容或发布记录。真实导入允许一到三套完整 Skill。

```json
{
  "schema": 1,
  "source": "chatgpt-maintenance",
  "source_saved": true,
  "save_evidence": "维护端对成功保存和完整导出的确认原文或可核实记录标识",
  "skills": [
    {
      "name": "script-visual-assets",
      "weekly_version": "1.0",
      "revision": "由维护端确认的唯一修订标识",
      "source_updated_at": "维护端成功保存的真实 ISO 8601 时间",
      "parent_content_sha256": null,
      "files": {"SKILL.md": "实际SHA-256", "references/实际文件.md": "实际SHA-256"},
      "restored_paths": []
    }
  ]
}
```

工具保留原始文件字节和相对路径；全量快照加原子更新清单，失败时不切换当前版本。快照不会原地覆盖。快照历史与 Git 提交共同提供追溯。

## 删除与撤回

最新版由完整清单指定，绝不与旧目录合并。删除文件进入 `removed_paths` 和持续保留的 `withdrawn_paths`，生产导出不带这些文件。恢复它们必须是维护端新的已保存修订，并显式列出 `restored_paths`。旧版本、旧修订、旧父摘要、过期保存时间或曾被替代的完整内容不能冒充新版本。

单个文件内部撤回的文字由完整文件替换消除，历史只保留用于审计。工具不理解所有规则的语义，无法自动辨认维护端在新文件里重新写入的一句旧规则；这种语义回退须通过维护端变更说明与差异核对判断，不声称自动防住一切回退。制作会话不得从历史快照或记忆中补回撤回规则。
