# 三套联动学习与迁移规则

修订：THREE-SKILL-INTEGRATION-20261017-01。依据用户2026-10-17明确要求；这是管理与交付检查规则，不是新效果实验。

## 每次都做，三套分别维护
每次学习、实跑反馈、复盘、候选审查或规则修订后，必须检查影视、漫画、资产三套，填写迁移矩阵；不得只更新当前对话所用的一套，也不得未经判断全文复制。只修改有实际增量的目标，纯重复建立已有规则指向。三套入口分别读取本文件与本包 cross-skill-adaptation.md。
共享构图、视觉注意力、空间、光影、色彩、材质与细节的检查原则；分别保留影视叙事、漫画原作推理、静态资产边界。项目设定、画风、角色、台词和比例不跨项目继承。

## 每日学习如何覆盖三套
1. 开始时读GitHub main的通道规则、三套现行入口、唯一主账和当天配额；列三套当前缺口。优先选能帮助多个媒介的真实问题，也为各套独有问题保留选题机会。
2. 三套合计仍为3次顺序技巧查询（候选→交叉→反证）和1次独立资讯查询。不是每套3次，不以每天各得1条为目标，不新增任务。资讯保持原广度要求，不能全缩成影视工具新闻。
3. 用当天实际候选逐一判断三套用途；若只适合一套，另两套给具体不适用原因，并把尚未覆盖的真实问题留在后续选题队列。不得虚构候选或为覆盖三套追加查询。
4. 收尾把审计、真实候选、人类简报及 cross-skill-transfer.json 写入 pending-review/YYYY-MM-DD/；八模块不减少，模块2说明三套价值、模块6分别报告验证状态、模块7报告各套变更与未改原因。
5. 简报仍为五部分、最多20行；“学到什么”最多3条，注明适用哪套、哪些仍待验证。同步/暂停日如实写未学习，不补跑；本次没有恢复暂停任务。

## 每条内容的迁移矩阵
字段必须包含：唯一条目ID、来源路径/提交和原认可范围；核心原则；影视/漫画/资产各自的用途、具体适配、现有规则位置、证据缺口、处理结果和不适用原因。
每个目标处理结果从 reuse_existing / adapt_pending_validation / approved_local_scope / not_applicable 中选择；这是迁移工作状态，不替代candidate等六状态。新效果候选仍在暂存区，原有三票门槛不变。
设计检查可按用户指令执行，但不能把“已安排”写成“已验证”。影视某次局部认可不自动成为漫画或图片效果的人类票、复现票或active。
跨套共用同一个case_id/证据源，目标复现分别记录；单次认可、归档或复用不拆成三次奖励。

## 视觉与输入的共同检查
- 写清观众先看哪里、读到什么；用构图、景别、主体占比、视线、清晰度或光影对比服务已确认信息，不能仅堆“震撼/电影感”。
- 核对左右前后、大小距离、出入口、视线、机位和物品归属；角色/道具身份一致与摄影机方向正确分开验收。
- 区分全片风格、当前场景光照和单镜/单图表现。确认主光方向、明暗与冷暖区域；分开描述金属、玻璃、布料、皮肤等材质，不把全部漫反射、浮尘、磨损或胶片品牌设为默认。
- 关键细节要与展示尺寸匹配；必要时安排有叙事用途的局部或补充图，不用文字解释替代画面可读性。不强制每镜特写、反打、变焦。
- 参考资产、构图图、首帧与状态帧用途分别登记；参考图不默认等于首帧。外观相同不保证空间正确，静态图正确不证明动作成功。
- 真实入口/模型/参数未知就保留未知，不以提示词质量词代替实际设置；未经目标生成验证，不宣称迁移改善了效果。
这些是既有约束的整合与用户要求的检查项；未验证的风格词、参考分工或首帧技巧仍按原状态隔离。

## 保存、授权与版本
GitHub main为规则、版本、账本、知识唯一真相源；旧云端彻底作废。先读仓库根 pending-review/channel-policy.json，以当前授权覆盖旧双端要求。
暂存区、审计报告、案例沉淀：创建PR、检查差异、自行合并、回读main；不等于候选自动转正。涉及任何核心升版（含本批资产/漫画拟V1.01）的PR，必须等待用户对该PR的明确合并指令；混合PR同样等待。
新分支的version.json只表示拟发布内容，用户查询现行版本必须读取main。三套共用影视包 references/audit/global-state.json，不创建新余额，本次0分0罚不追溯。
